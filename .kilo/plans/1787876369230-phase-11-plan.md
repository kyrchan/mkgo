# Phase 11 Plan: VFIO Foundation + Framebuffer

## Context
Phase 11 aims to provide VFIO (Virtual Function I/O) foundation for device passthrough and a framebuffer-only policy for graphics. The kernel VFIO foundation is being implemented in `core/vfio.cc` and `core/pci.cc`. A Go graphics driver exists at `services/graphics/main.go` that uses the VFIO mappings to render to the framebuffer. The gate requires displaying `cat /etc/motd` output through `graphics.wasm` to a visible console window (framebuffer writes reach the screen).

## Decisions
- Follow the VFIO foundation design as outlined in `AGENTS.md` lines 220-255.
- Use the existing kernel VFIO code as a starting point.
- The graphics driver will render text to the mapped framebuffer BAR and use `kern_fb_present` to copy to the physical LFB.
- Legacy devices (PS/2, PIC, etc.) will be implemented as tiny frozen shims in `arch/x86_64/` (out of scope for this plan but noted).

## Risks
- Missing capability checks in kernel VFIO functions (e.g., `CAP_FB`, `CAP_PCI`).
- Guest library (`guests/lib`) may not expose all required kernel functions (e.g., `PciEnableBusmaster`).
- Framebuffer address mapping and cacheability (write-combining) must be correctly set.
- Synchronization between guest rendering and host presentation (via VSYNC doorbell) may need refinement.
- Legacy device shims not covered by VFIO may require separate implementation.

## Validation Steps
1. Build the kernel and graphics.wasm module.
2. Boot QEMU with the kernel and graphics module loaded.
3. Verify that the graphics driver initializes without errors (GPU found, BAR mapped, mode set).
4. Check that the rendered text (e.g., "Phase 11 VFIO framebuffer") appears in the QEMU VGA window (or via framebuffer dump).
5. Ensure that the gate strings from `make test` (or equivalent) for phase 11 are present in the serial log.
6. Run any existing phase 11 validation tests (if any) or create a simple test that confirms framebuffer writes reach the screen.

## Open Questions
- Is the IOMMU implementation complete enough to securely restrict DMA to assigned pages?
- Does the guest lib provide wrappers for all VFIO kernel functions used by the graphics driver?
- Are the legacy device shims (PS/2, PIC, UART, PCI config) implemented as frozen shims in `arch/x86_64/`?
- Does the framebuffer present function correctly copy the guest window to the physical LFB with the correct pixel format and stride?

## Suggested Tasks (for implementation agent)
1. Review and complete kernel VFIO foundation in `core/vfio.cc` and `core/pci.cc`:
   - Ensure IOMMU domain management correctly tracks and restricts DMA.
   - Verify MSI-X programming and doorbell handling.
   - Confirm framebuffer functions (`fb_set_mode`, `fb_set_cursor`, `fb_present`) handle capabilities and memory mapping correctly.
   - Check that `PciMapBar` grants IOMMU ownership and extends guest memory as needed.
   - Validate that `PciBindIrq` correctly allocates vectors and programs MSI-X table.
2. Review and update the guest library (`guests/lib`) to expose necessary kernel functions:
   - `PciEnableBusmaster`
   - `PciBindIrq` (with IRQ type)
   - `PciUnmapBar`
   - `FbSetMode`, `FbSetCursor`, `FbPresent`
   - Devman ENUM for class 10 devices
3. Test the graphics driver in isolation with a mock kernel to ensure it calls the correct functions.
4. Integrate and test the full stack in QEMU, verifying the gate condition.
5. Implement legacy device shims (if not already) as tiny frozen shims in `arch/x86_664/` (out of scope for this plan but may be needed for full boot).
6. Update any necessary capability bits in `sched.h` or kernel registry for VFIO and framebuffer access.

Note: This plan is intended to be executed by an implementation-capable agent. No source edits should be made by this planner.

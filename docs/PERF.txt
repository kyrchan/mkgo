1. INTRODUCTION

1.1 Scope. This document analyzes the performance characteristics of the
     capability microkernel subsystems, with emphasis on VFIO passthrough
     (Phase 11), memory management, and scheduler overhead. Measured numbers
     are from QEMU 10.0.11 (q35, -cpu max, 512 MiB guest) under TCG; KVM
     estimates are noted where applicable.

1.2 Measurement environment. TCG is 10-50x slower than KVM for syscall-heavy
     workloads. All "native est." figures assume KVM or bare metal. VFIO
     estimates derive from code-path analysis of core/vfio.cc and standard
     PCIe characteristics.

2. WASI IMPORT CALL OVERHEAD

2.1 wasm3 runtime cost. Each kern_* import crosses the wasm3 ↔ native boundary:

Operation                       | TCG (μs) | Native est. (ns) | Notes
--------------------------------+----------+------------------+---------------------------
kern_port_send (4096 B)         | 10-30    | 2000-5000        | 2 memcpy (guest→kern→dest)
kern_port_recv (poll)           | 5-15     | 500-2000         | 1 memcpy if data present
kern_pci_read32                 | 3-8      | 200-500          | PCI cfg read + validation
kern_pci_write32                | 3-8      | 200-500          | PCI cfg write + validation
kern_pci_map_bar (one-time)     | 500-2000 | 5000-20000       | ResizeMemory + IOMMU map
kern_doorbell_wait (wake)       | 20-50    | 5000-20000       | ctx switch + pending check
sched_yield                     | 3-10     | 200-500          | coroutine switch (~34 LOC)

2.2 Crossing cost breakdown. A kern_* import invokes m3_CallRuntime which:
     a. Validates guest pointer against [base, base+size) via mem_ok().
     b. Marshals WASM stack args to native registers.
     c. Executes the C++ raw function.
     d. Marshals return value back to WASM stack.
     The overhead is dominated by pointer validation + marshaling, not the
     operation itself. Batch amortization is critical for high-frequency ops.

3. VFIO DOORBELL BATCHING

3.1 Problem: yield-polling. IRQ-bearing devices without doorbells require:
     while (!data) { kern_port_recv(h, buf, cap); sched_yield(); }
     Cost per poll: 2 imports × ~5 μs (TCG) = ~10 μs minimum.
     At 100k polls/sec: 100% CPU spent polling — no work done.

3.2 Doorbell batching math. kern_doorbell_wait blocks until IRQ fires:

Scenario: net.wasm at 100k packets/sec
     Yield-polling: 100k polls × 10 μs = 1000 ms/sec (100% CPU)
     Doorbell (1000 pkt batch): 100 wakes × 10 μs = 1 ms/sec (0.1% CPU)
     Savings: ~1000x reduction in scheduling overhead.

3.3 Doorbell latency. vfio_doorbell_wait costs:
     - Wake path: timer ISR → vfio_fire_doorbell → pending=true → switch to
       waiting session. Est. 5-20 μs (native), 20-50 μs (TCG).
     - Level-triggered: if IRQ fired while not waiting, immediate return (0 μs
       additional latency on next wait call).

3.4 Batch size tradeoff. Larger batches = lower overhead but higher latency:
     Batch 1:    latency = 1/throughput, overhead = 100%
     Batch 1000: latency = 1ms@100kpps, overhead = 0.1%
     Optimal: batch until deadline (e.g. 16ms frame time at 60fps).

4. FRAMEBUFFER WRITE-COMBINING

4.1 Why WC is required. PCI framebuffer BARs MUST be mapped write-combining:
     - Normal WB caching: writes buffer in CPU cache lines, defeating write
       combining; reads from WB device memory cause stalls.
     - WC: CPU buffers up to 64 bytes (one cache line) before flushing to bus.
     - UC (uncacheable): every write hits the bus immediately — 10-100x slower.

4.2 Performance impact. 1920×1080×32 @ 60fps = 497 MiB/sec fill rate:

Mapping   | Write cost/frame | Total @ 60fps | Notes
----------+------------------+---------------+---------------------------
WB        | unusable         | N/A           | Read stalls, corruption
UC        | 50-100 μs        | 3-6 ms        | Every write to bus
WC        | 2-5 μs           | 0.12-0.3 ms   | Cache-line bursts

4.3 WC vs uncacheable. UC is safest (immediate bus visibility) but kills
     throughput. WC is the standard for Linux/Windows framebuffers. The kernel
     maps framebuffer BARs as WC (is_wc flag in bar_map) and device-register
     BARs as UC via PAT/MTRR programming.

4.4 VFIO framebuffer data path. Guest writes pixels directly to mapped LFB
     window (zero kernel copy during rendering). On VSYNC, vfio_fb_present
     copies guest linear memory at win_off to identity-mapped physical LFB.
     For 1024×768×32: 3 MiB/frame × 60 fps = 180 MiB/sec copy bandwidth.
     Cost: ~1-3 ms/sec native (hardware memcpy), negligible on KVM.
     On real IOMMU hardware: zero-copy (guest physical == LFB physical).

5. ZERO-COPY DATA PATH

5.1 Design principle: no kernel copy for VFIO MMIO. PCI BARs map directly
     into guest linear memory. Guest load/store instructions reach hardware
     with zero kernel involvement (identity mapping: physical == virtual).

5.2 BAR mapping cost (one-time). vfio_map_bar performs:
     a. CAP_PCI check: O(1) capmask lookup.
     b. BDF assignment check: O(16) scan of assigns[] table.
     c. pci_bar_info probe: 4-6 PCI config reads/writes.
     d. alloc_window: O(1) bump allocator.
     e. ResizeMemory: one-time wasm memory extension (64 KiB pages).
     f. iommu_map_pages: O(n) for n 4-KiB pages in BAR.
     g. Record insertion: O(8) scan of bar_maps[].
     For 32 MiB framebuffer BAR: ~256 IOMMU page records, ~1-2 ms one-time.

5.3 Runtime MMIO cost. After mapping, each guest MMIO access is a regular
     load/store to the mapped window. No import crossing, no kernel trap
     (except first-access page fault if not pre-faulted).
     Cost: 1-5 ns (native, TLB hit), 50-200 ns (TCG).

5.4 DMA performance. With bus mastering enabled (kern_pci_enable_busmaster),
     the device performs DMA directly to/from guest pages. IOMMU domain
     tracking ensures the device can only access assigned pages. DMA bandwidth
     limited only by PCIe link — no kernel copy overhead.
     PCIe 3.0 x16: up to 16 GiB/s achievable.

5.5 Descriptor rings (virtio). virtio-net/virtio-blk use paravirtual rings
     with kernel-owned descriptors. Guests interact via queue windows (§6/§3).
     VFIO maps physical device BARs directly; guests interact via MMIO.
     VFIO achieves near-native (guest driver unmodified); virtio achieves
     good performance with simpler kernel code.

6. MEMORY MANAGEMENT

6.1 Bump allocator (mm.cc). mm_alloc(bytes, align) returns pages from pool:
     - Allocation: O(1) — bump pointer advance, no free list.
     - Free: not supported (pages never returned).
     - Cost: ~10-50 ns (native) — single pointer add + alignment mask.
     - Use: session stacks (1 MiB), VFIO BAR backing buffers, module blobs.

6.2 Binned allocator (rt.cc). Byte allocator for engine/libc needs:
     - Bins[NCLASS] singly-linked free lists, class c covers 2^c bytes.
     - Allocation: O(1) — pop from free list or split larger block.
     - Free: O(1) — push to appropriate bin.
     - Oversized (cls_of >= NCLASS): exact mm_alloc, intentionally leaked.
     - Cost: ~50-200 ns (native) — list traversal + possible split.

6.3 Page table cost. Flat/identity mapping everywhere (no per-arch page
     tables): x86-64 identity map, arm64 MMU off, riscv64 bare M-mode.
     - TLB miss cost: 0 (no page table walk on identity map).
     - Isolation: engine bounds checks, NOT MMU. Cost: ~5-10 ns per access
       (single comparison against memory base+size).

6.4 Session isolation overhead. Each session has independent wasm3 runtime
     with own linear memory. No cross-session memory access possible:
     - Engine bounds check: if (ptr < base || ptr+len > base+size) trap.
     - Cost: ~5-10 ns per import (two comparisons + branch).
     - No TLB flush on context switch (flat mapping, no ASIDs needed).

6.5 Memory footprint per session:

Component             | Size        | Notes
----------------------+-------------+---------------------------
WASM runtime          | ~64 KiB     | m3_NewRuntime overhead
WASM stack            | 64 KiB      | STACK_SLOTS(8192)*8 bytes
Native stack          | 1 MiB       | mm_alloc for coroutine
Linear memory         | 64 KiB+     | grows via ResizeMemory
WASI state            | ~2 KiB      | argv, fds[64], errno
VFIO domain           | ~8 KiB      | iommu_domain (256 pages)
Total per session     | ~1.2 MiB    | + module code + data

7. SCHEDULER

7.1 Context-switch cost. Coroutine switching (arch/x86_64/ctx.S, ~34 LOC):
     - Save/restore: RIP, RSP, callee-saved registers (RBX, RBP, R12-R15).
     - Cost: ~10-30 ns (native), ~200-500 ns (TCG).
     - No kernel/user mode transition (all in ring 0).
     - No TLB flush (flat mapping, global pages).

7.2 Scheduling policy. Cooperative round-robin (Phase 3) with IRQ-preemptive
     RR available (Phase 8):
     - Quantum: configurable via /etc/kernel.conf (quantum_ms).
     - Default: cooperative (yield/proc_exit points).
     - Preemptive: timer ISR fires, scheduler picks next RUNNABLE session.
     - Budget: ≤400 LOC (queues + timer hookup).

7.3 Quantum tradeoffs:
     Quantum | Latency | Throughput | Notes
     --------+---------+------------+---------------------------
     1 ms    | 1 ms    | ~95%       | 5% overhead @ 1000 switches/s
     10 ms   | 10 ms   | ~99%      | 1% overhead @ 100 switches/s
     100 ms  | 100 ms  | ~99.9%    | 0.1% overhead @ 10 switches/s
     Cooperative | ∞  | ~100%     | No preemption overhead

7.4 No-starvation guarantee. Round-robin ensures each RUNNABLE session gets
     a turn. Busy-loop session cannot block second session (preemptive mode).
     Cooperative mode: busy loop must yield eventually or starve others.

     - Est: ~50-200 ns (native) for typical DMA target.
     - Only checked on VFIO foundation calls, not on every MMIO access.

9. COMPARATIVE ANALYSIS

9.1 VFIO vs virtio-net:

Metric              | VFIO (passthrough) | Virtio (paravirtual)
--------------------+--------------------+--------------------
Throughput          | Line rate          | ~80% line rate
Latency             | ~1-5 μs            | ~5-20 μs
CPU overhead        | ~0.1%              | ~1-5%
Kernel code         | 0 per device       | ~600-900 LOC/shim
Guest driver        | Unmodified         | virtio-net driver
Portability         | Needs IOMMU        | Universal

9.2 VFIO vs class-window shim:

Metric              | VFIO BAR mapping   | Class window (§3/§6)
--------------------+--------------------+--------------------
Guest access        | Direct MMIO        | Window offsets
Kernel copy         | Zero               | Zero (window in guest mem)
Setup cost          | ~1-2 ms one-time   | Instant (window pre-assigned)
Flexibility         | Any PCI device     | Fixed window layout

11. BOTTLENECK ANALYSIS

11.1 Highest-cost operations (avoid in hot paths):
     - kern_pci_map_bar: one-time only, cache the window offset.
     - vfio_fb_present: called once per frame, not per draw call.
     - fs_roundtrip (routed fd): use direct-port FSClient for throughput.

11.2 Lowest-cost operations (safe for hot paths):
     - MMIO access (after BAR mapping): 1-5 ns, direct load/store.
     - Doorbell wait: 5-20 μs wake, zero polling overhead.
     - Port send/recv: 2-5 μs, acceptable for message-passing.

11.3 Optimization guidelines:
     a. Batch doorbell waits: drain N packets per wake, not 1.
     b. Pre-map BARs at session init, not in packet path.
     c. Use WC mapping for framebuffer BARs (is_wc flag).
     d. Avoid routed preview1 for high-throughput FS ops.
     e. Pre-allocate guest memory to avoid ResizeMemory in hot path.
